## 1. 结论摘要

1. 报告的**事实判断全部成立**。§11 给出的 11 组深色对比度、以及 §2.1 里对现状的 5 组批评数值  
   （辅助文字 3.13:1、占位 2.37:1、成功绿 2.41:1、金色 2.03:1、推荐黄底日期 2.83:1），  
   我用 sRGB 相对亮度公式全部独立复算，**逐项吻合**，无一处偏差。
2. 深色模式已按报告的三层机制实现：**原生窗口层（theme.json + app.json `@变量`）→ 自绘层  
   （styles/tokens.wxss 语义令牌 + `prefers-color-scheme`）→ JS/位图层（utils/theme.js + 图标 tone）**。
   模拟器实测：六个页面在浅色/深色两态下均无白色残留，深色配色与方案 §4 一致。
3. 首期**只做跟随系统**（报告 §7.1 的推荐行为），不提供手动切换；切换时不重新加载业务数据。
4. 报告 §2.2 的交互问题中，**6 项已落地**、**3 项按报告建议改法落地**、**1 项落地后经实测回退**（§11.2）、
   **3 项记入存疑**（§3）。
5. 报告 §8「不能漏掉的边界」里，**原生地图深色瓦片**与**自备 marker 位图**本轮**未做**，  
   属于已知的部分适配（模拟器截图已确认：附近页界面层深色 + 底图仍浅色），理由与待决策点见 §3.3。
6. ⚠️ **连 IDE 实测暴露了 2 个离线判据查不出来的问题**（静态判据全绿时它们是隐形的），  
   两个都已修复并补了回归防线 —— 详见 **§11**。这是本项目「静态判据不能替代一次真机/模拟器实测」的又一次实证。

## 3. 存疑与未采纳项（需要你拍板或说明理由）

### 3.1 ⏸ 控件命中面积（报告 §2.2 P1）

报告建议独立按钮目标 44px（88rpx），并指出彩种选项 52rpx(26px)、选号球 72rpx(36px) 偏小。

**没有改**，理由：

- 彩种切换器是**分段控件**（3 个选项共处一个 88rpx 高的容器里）。把单项撑到 44px，只能靠加大容器高度或靠  
  `padding` + 负边距「偷」命中区 —— 后者会让相邻选项的命中区**互相覆盖**，点大乐透误触双色球的概率反而上升。
- 这与已冻结的设计稿尺寸（52rpx 胶囊 / 72rpx 选号球 / 38rpx 日历格）直接冲突。
- 日历格报告自己也判为「高密度例外」，且已按报告要求补上「选中描边 + 详情区文字判读」。

**请你选一个**：

1. 接受现状（设计优先），只在真机体验后再决定；
2. 把彩种切换器与选号球整体放大到 88rpx 命中高度（会改变设计稿外观，需要同步更新设计稿与需求文档）；
3. 折中：仅把**彩种切换器**放大到 72rpx 高、选号球保持 72rpx 但把「已选满」状态做得更明确。

### 3.2 ⚠️ 首页配置入口的位置（与报告建议不一致）

报告写「放在不与微信右上胶囊冲突的位置」。按字面最自然的读法是导航栏右侧，  
但**导航栏右侧就是微信右上角胶囊的地盘**（本项目导航栏高度本身就是按胶囊对齐算出来的），  
因此改为**标题旁内联胶囊**：`您好，春生  [配置 ›]`。这样既有可见的点击提示，  
又与胶囊无冲突，也不需要新增第五个 Tab。

### 3.3 ⏸ 原生地图深色瓦片（报告 §8.1）

报告 §8.1 的技术判断成立，我核对后确认：

- 个性化地图**必须**用 `subkey` + `layer-style`，且 `subkey` 不支持动态修改，样式能力需购买授权；
- 当前 `pages/nearby/nearby.wxml` 的 `<map>` **未绑定** `subkey` / `layer-style`。

**本轮未做**，也没有盖半透明黑层、没有加反色滤镜（报告已明确反对，我同意）。  
因此「附近」页在深色下是：**界面层全深色 + 原生底图仍为默认浅色**，属于**部分适配**，  
不宣称完整夜间模式。

**需要你决定**：是否申请/购买个性化地图样式授权。拿到授权后我按报告建议的顺序做  
（浅/深两套 style → 固定合法 subkey → `layer-style` 切换 → 真机验证是否需重建 map）。

### 3.4 ⏸ 按压反馈的剩余项（报告 §2.2 P2）

已覆盖主要可点项（见 §2.2 表）。**未覆盖**：

- 首页彩种切换器的**选中项**：`hover-class` 是静态类名，无法按选中态换色。若统一给  
  `press-surface`，按下已选中的黑色胶囊会闪成浅灰，属于「看起来像故障」的反馈，比没有反馈更糟。
- 地图上的 marker（原生组件，不受 WXSS 控制）。
- 纯展示卡片（如首页开奖信息卡非按钮区域）。

**请你决定**：是否引入「按压只加深描边、不改底色」的第二套 press 类来覆盖剩余项。

### 3.5 ⏸ 抽屉把手拖拽手势

报告写「若不实现拖拽，把手作为弱视觉提示，不在文案中声称可以下滑」。核对现状：  
把手无拖拽事件，**文案也从未声称可下滑** → 已满足报告要求。  
真实拖拽关闭**未实现**（需要真机调手势冲突、正文滚动与拖拽区互斥），列为后续项。

### 3.6 🔧 比报告更进一步的两处改动（可回退）

1. **删除全部 `--color-*` 旧变量**（报告只要求「拆分职责」）。  
   我把旧名整块删掉而不是保留映射，因为 `--color-ink` 一名三义正是深色事故的诱因 ——  
   留着它，后来者还会拿它给按钮上色。已确认全工程（含 WXML 内联样式）**零引用**后才删。  
   回退方式：在 `app.wxss` 的 `page{}` 里加回映射即可（见 §6）。
2. **`check_miniprogram.py` 的「推荐页 mtime 冻结」改为内容断言**。  
   报告 §1 / §6.6 明确把推荐页列入必须覆盖的六个页面，深色适配一定要改  
   `pages/recommend/*`，而原判据按 mtime 判「今日不得改动」→ 必然误报。  
   改造方式与 2026-09-15 对 `backend/src`、`utils/api.js` 的处理**完全同构**：  
   不看 mtime，改为断言「文件仍在 + 关键能力符号仍在（两套体系 / 四注组合 / 号码卡 /  
   分析抽屉 / 免责声明 / 红蓝球样式）」。**眼镜端目录仍保持最严格的 mtime 冻结**。  
   如果你希望推荐页继续硬冻结，需要先明确「深色模式不覆盖推荐页」。

## 4. 深色模式的实现机制（三层）

| 层        | 文件                                                       | 职责                                                                                                                      | 关键约束                                                                       |
| -------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 原生窗口层    | `theme.json`（新增）、`app.json`                              | 提供 light/dark 两套 `navigationBarTextStyle` / `backgroundColor` / `backgroundTextStyle` / tabBar 四色；`app.json` 用 `@变量` 引用 | **只写深色媒体查询不够**：原生窗口（下拉背景、tabBar 兜底色）读的是 app.json，不是 WXSS                   |
| 自绘层      | `styles/tokens.wxss`（新增，唯一真相源）+ `app.wxss` + 各页 `*.wxss` | `page, .tabbar` 上定义浅色基准令牌；深色媒体查询只覆盖同名令牌的**值**，不重写任何规则；页面只写 `var(--token)`                  | ⚠️ 令牌**必须**放在 `styles/tokens.wxss` 并由每个「脱离 page 的组件」自行 @import —— 自定义 tabBar 是 page 的兄弟节点，`page{}` 的变量继承不进去（§11.1 事故）。页面里出现一处裸色值，深色下就亮一块（已用脚本兜住，§7） |
| JS / 位图层 | `utils/theme.js`（新增）、`app.js`、`components/icon/index.js` | `icon` 组件把图标渲染成 SVG 的 data URI，**CSS 变量进不了那个字符串**，必须由 JS 解析实际色值；组件订阅主题变化后重新生成 URI                                       | 全工程只建立**一条**主题监听链（`theme.js` 内的单例），页面/组件用 `subscribe()` 拿取消函数在卸载时解绑，避免重复注册 |

补充说明：

- 「跟随系统」由三处入口保证一致：`App.onLaunch` 初始化 → `App.onShow` 回前台校准  
  （部分平台在后台期间不补发 `onThemeChange`）→ `wx.onThemeChange` 实时事件。
- 主题切换**只改样式与展示资源**：不触发 `loadData()`、不重新 OCR、不重新生成推荐；  
  当前页、滚动位置、草稿、选中日期、已展开抽屉、地图中心与缩放级别均不受影响。
- 渲染器未切换。`app.json` 里虽然写着 `rendererOptions.skyline`，但页面未声明  
  `renderer: skyline`，实际仍走 WebView —— CSS 变量与 `prefers-color-scheme` 均可用，  
  按报告要求**不擅自切换渲染器**。

## 11. 连 IDE 实测暴露并修复的 2 个问题（离线判据查不出来）

> 离线判据当时**全绿**。这两个问题都是「CSS 生效了但结果不对 / 声明被静默丢弃」的类型，
> **只有跑起来看才知道**。教训：静态判据能防「漏」，防不了「错」。

### 11.1 🔴 底部导航整块失去颜色（用户报障：「底部导航栏都没有了，按键就这么悬浮着」）

**现象**（`_dev_tools/_ide_shots/_ide_home.jpg` 为修复前实拍）：
底部 4 个 tab 的文字与图标还在、位置也在，但**胶囊容器白底、边框、选中项黑底全部消失**，
看起来像一排按键浮在页面上。**console 无报错、编译无警告、没有任何提示。**

**根因**：自定义 tabBar（`custom-tab-bar/`）**渲染在 `page` 节点之外**，它是 page 的**兄弟节点**
而不是子节点。因此 `app.wxss` 里 `page { --x: ... }` 定义的 CSS 变量**不会继承**进组件内部 ——
组件里每一条 `var(--x)` 都解析失败、整条声明被丢弃。

> 注意这与 `styleIsolation` 无关：`apply-shared` 只能让「选择器能匹配到的」节点生效，
> 而 `page` 元素压根不是它的祖先。我一开始加的 `apply-shared` 属于**错误归因**，已一并回退。

**修复**：抽出 `styles/tokens.wxss` 作为令牌唯一真相源，选择器写成 `page, .tabbar`
（浅色段与深色段各一份），由 `app.wxss` 与 `custom-tab-bar/index.wxss` **各自 @import**。
同时把「脱离 page 的组件必须自行 @import 令牌文件」固化成判据，并做了反向验证（§7）。

**修复后实拍**：`_ide_shots/_ide_home2.jpg`（浅色）/ `_ide_home4_dark.jpg`（深色）—— 胶囊与选中态均恢复。

### 11.2 ⚠️ 底栏位置被顶高约 30px（用户报障：「底部导航栏位置有点偏上了」）

**原因**：我按报告 §2.2 把内边距改成 `calc(44rpx + env(safe-area-inset-bottom))`，
在带 Home 指示条的机型上 `env()` = 34px，直接把胶囊顶高。

**量测取证**（像素级，非目测）：

| 截图 | 选中胶囊底边距屏幕底边（图内 px） |
|---|---|
| 浅色 · 回退前 `_ide_home2.jpg` | 76 |
| 浅色 · 回退后 `_ide_home3.jpg` | **33**（下移 43） |
| 深色 · 回退前 `_ide_dark_home.jpg` | 79 |
| 深色 · 回退后 `_ide_home4_dark.jpg` | **40**（下移 39） |

**结论与处置**：胶囊是**悬浮**元素而非通栏，设计稿的 22px 底部留白本身已越过 Home 指示条，
**不需要再叠安全区**。已回退为设计稿原值 `padding: 20rpx 42rpx 44rpx`，`.page-bottom-safe` 一并
回退为 `200rpx`（= tabBar 自身高度 188rpx + 余量，与原设计一致）。
抽屉（全宽、贴屏底）继续保留 `env(safe-area-inset-bottom)` —— 那才是真正需要它的地方。

**教训**：报告这条写的是「按安全区计算底部距离……**真机验证，不直接判定当前必然遮挡**」，
我把「真机验证」这一步跳过了就直接改。**报告里标了「需验证」的建议，不能在没验证时当成已确认的结论。**
